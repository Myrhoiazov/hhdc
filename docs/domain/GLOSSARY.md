# HHDC Admin — Domain Glossary

Canonical vocabulary for HHDC Admin, extracted from the current codebase. Terms are grounded in
`server/prisma/schema/*.prisma` and the controllers/services that implement them. Where meaning
couldn't be confirmed in code, it's marked **Needs clarification** rather than guessed.

| Term | Meaning in HHDC Admin | Related concepts | Notes |
|---|---|---|---|
| Client | A person enrolled at the school (student), or their parent/guardian who pays. Never authenticates — no login path exists for `Client`. | Branch, Comment, ClientDanceGroup, Customer | [crm.md](crm.md) |
| Student | Same entity as **Client** — the code and UI use "student" and "client" interchangeably; there is no separate Student model. | Client | — |
| User | A staff member (role `ADMIN`/`MANAGER`/`DOCTOR`). Distinct from Client — Users are the only entities that authenticate. | Session, AuthSecurityEvent | `DOCTOR` role exists but gates nothing in code — **Needs clarification** (no rationale found for the name or intended use). |
| Group / Dance group | A scheduled class: style (free text) + level (`START`/`FAN`/`PRO`) + choreographer + hall + branch + price. Modeled as `DanceGroup`. | Choreographer, Hall, ScheduleSlot, Branch | `maxParticipants` is stored but not enforced anywhere in code — informational only. [scheduling.md](scheduling.md) |
| Choreographer | An instructor who teaches one or more groups. | DanceGroup | [scheduling.md](scheduling.md) |
| Branch / Filiya | A physical location/studio. | Client, DanceGroup, LegalOrganization (indirectly, via billing brand) | Hard-deletable (no soft-delete gate), despite having an `isActive` field. [organization.md](organization.md) |
| Legal Organization | The studio's own legal entity (KVK/VAT numbers, bank details, registered address). Treated as a singleton by controller convention (`findFirst`, not a schema constraint). | BusinessBrand | [organization.md](organization.md) |
| Business Brand | A billing identity (name, logo, primary color, contact info) used as the *issuer* on invoices. One organization can have multiple brands; exactly one may be `isDefault` at a time (enforced transactionally). Deletion is always a soft archive (`isActive: false`), never a hard delete. | LegalOrganization, Invoice | [organization.md](organization.md) |
| Invoice | Billing document issued to a client (or a free-text bill-to party). Generated for active groups. PDF + online payment link. Status (`DRAFT`/`ISSUED`/`PARTIALLY_PAID`/`PAID`/`OVERDUE`/`CANCELLED`) is **derived/recomputed on every mutation**, not a freely-set field. | InvoiceItem, InvoicePayment, InvoiceDelivery, BusinessBrand | [billing.md](billing.md) |
| Credit note / Debit note | Adjustment documents linked to a parent `Invoice` via `parentInvoiceId`. A credit note reduces the parent's balance (capped at the parent's total); a debit note is a standalone new billable document that does **not** touch the parent's balance — the two are asymmetric despite sharing one API. | Invoice | [billing.md](billing.md) |
| Mollie | Payment gateway integration: OAuth-connected customer profiles, subscriptions, mandates, payments, webhook-driven reconciliation. | Customer, Mandate, Subscription, Payment | [payments.md](payments.md) |
| Customer (Mollie) | A Mollie-side payer profile. Distinct from `Client` — one `Customer` (payer, e.g. a parent) can fund multiple `Client`s (students) via `CustomerClientLink`. `Customer.clientId` is a denormalized cache of whichever link is currently primary, not the source of truth. | Client, CustomerClientLink, Mandate | [payments.md](payments.md) |
| Mandate | Recurring payment authorisation (Mollie) tied to a `Customer`. | Subscription | [payments.md](payments.md) |
| Subscription | A recurring payment plan (Mollie) tied to a `Mandate`/`Customer`, with a `nextPaymentDate`. | Mandate, Payment, PaymentReminderDelivery | [payments.md](payments.md) |
| Payment (Mollie) | A single Mollie transaction (`Payment` model, `mollieId` prefix `tr_`). May be linked to an `Invoice`, a `Subscription`, both, or neither. | Invoice, Subscription, MollieEvent | [payments.md](payments.md) |
| Transaction | Manual, internal cash bookkeeping (income/expense) for the studio — rent, supplies, etc. **Unrelated to client invoicing.** Merged with synced Mollie payments at read time into a reporting-only `FinancialTransaction` view (`source: 'MANUAL' \| 'MOLLIE'`); nothing is written back from that merge. | — | [payments.md](payments.md). Do not confuse with `InvoicePayment` (a payment recorded *against* an invoice) or Mollie `Payment`. |
| InvoicePayment | A manually recorded payment applied to a specific `Invoice`'s balance. Distinct from the internal `Transaction` ledger and from a Mollie `Payment`. | Invoice | [billing.md](billing.md) |
| Reminder — **two distinct mechanisms, do not conflate** | **(1) Invoice reminder**: `InvoiceDelivery` with type `REMINDER_BEFORE_DUE`/`REMINDER_OVERDUE`, about an unpaid **invoice** balance, owned by Billing (`modules/invoices/invoices.reminders.service.ts`). **(2) Payment reminder**: `PaymentReminderDelivery`, about an upcoming recurring-**subscription** charge (`Subscription.nextPaymentDate`), owned by Payments (`modules/payment-reminders/payment-reminders.service.ts`). They share no code, no data, and notify about different things. | InvoiceDelivery, PaymentReminderDelivery, Subscription | See [billing.md](billing.md) and [payments.md](payments.md). |
| Incident (Mollie) | Not a stored entity — a **derived query** over existing tables: a payment in a failed/canceled/expired/charged-back state, a live subscription with no valid mandate, or a customer with no email/no client link. "Resolving" one just logs an acknowledgement (`MollieIncidentResolution`) that excludes it from future incident queries — it does not change the underlying record. | Payment, Subscription, Customer | [payments.md](payments.md) |
| EmailAccount | A staff-configured IMAP+SMTP mailbox connection. Entire `/email` API is `ADMIN`-only. | EmailMessage | [communication.md](communication.md) |
| Comment | A staff note attached to a client. The `entityType` field looks generic but only `'client'` is implemented today. | Client | [crm.md](crm.md) |
| ClientStatus | Model exists (`loyaltyLevel`, `notes`) but **no controller or service in the current codebase reads or writes it**. **Needs clarification** — likely unused/legacy, or owned by a part of the codebase not covered by this documentation pass; do not assume loyalty-tier logic is active. | Client | [crm.md](crm.md) |
| isActive vs isEnabled (User) | `isEnabled` is the real access gate (checked on every login/session lookup; an admin cannot disable their own account). `isActive` defaults to `false` and, in the code read for this documentation, is **never written past its default and never read for any access decision** — effectively a dead field today. **Needs clarification** for intended future use. | User | [identity.md](identity.md) |
| Session | A staff login session (opaque token, hashed at rest). Rotated on refresh; revoked on logout. | User, AuthSecurityEvent | [identity.md](identity.md) |
| TwoFactorChallenge | A short-lived record bridging "password accepted" and "2FA code confirmed." Does not grant access on its own. | User, TrustedDevice | [identity.md](identity.md) |
| TrustedDevice | A cookie-bound device record that lets a returning user skip the 2FA challenge for 30 days. | User, TwoFactorChallenge | [identity.md](identity.md) |
| Telegram notification | A one-way service message the bot sends to staff — not a customer channel. Seven types: new student, new Mollie customer, Mollie payment, login blocked, new device after failures, role changed, new email. All go to the shared admin group except new email, which goes to one admin's private chat. | Notification switch, TelegramNotificationSetting | [communication.md](communication.md), [spec](../spec/DDC_CRM_TELEGRAM_NOTIFICATIONS_SPEC.md) |
| Notification switch | The `ADMIN`-controlled on/off state of one Telegram notification type, managed on the `/notifications` page ("Уведомления"). Stored as `TelegramNotificationSetting` only once changed; until then the type's code default applies. Every change is announced to the admin group. | Telegram notification, User | Distinct from **Reminder** (emails to payers) and from AI draft approval messages. |
