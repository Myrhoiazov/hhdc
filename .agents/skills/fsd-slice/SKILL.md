# FSD-слайс в клиенте

Справка — слои, куда положить код, анатомия слайсов, связи между сущностями, стор и тесты — в
[fsd-architecture.md](../../rules/fsd-architecture.md). Прочитай её целиком до первого шага.

## Генератор

`npm run generate:slice <entities|features|widgets|pages> <Name>` из `client/` создаёт слайс по анатомии из правила:

- сущность — `model/types.ts`, `api/<name>Api.ts` с запросом-заготовкой через `readData`, `index.ts`;
- фича и виджет — компонент в `ui/<Name>/` со своим SCSS-модулем и `index.ts`;
- страница — `ui/<Name>Page.tsx` в `CrmLayout`, `ui/<Name>Page.async.tsx` и `index.ts` с ленивой версией.

Генератор проверяет имя по слою (сущность, виджет, страница — PascalCase, фича — camelCase «действие + объект»;
к странице дописывается `Page`) и не трогает существующий слайс. Созданные файлы проходят Prettier, ESLint и
TypeScript без правок; дальше — шаги 2–8 из раздела «Новая сущность», а странице ещё нужен маршрут в
`RoutePath` и `routeConfig`.

## Новая сущность: шаги

1. **Назови и найди место.** Возьми термин из `CONTEXT.md`, проверь `ls client/src/entities`: запись, которую уже
   описывает существующая сущность, расширяет её. Готово, когда выбрано одно имя в PascalCase и нет второй
   сущности с тем же смыслом. Затем создай каркас генератором (раздел выше).
2. **Опиши типы.** Интерфейсы ответа сервера и константы (`*_STATUSES as const`, размеры страниц) — в
   `model/types.ts`. Готово, когда каждый тип, который вернёт `api/`, объявлен здесь.
3. **Опиши запросы.** `api/<name>Api.ts` разворачивает ответ сервера через `readData`, `readPage`, `postData`,
   `patchData`, `putData`, `deleteData` из `@/shared/api/request`; `$apiPrivate` напрямую — только для ответа
   без обёртки `data` (файл как `Blob`). Готово, когда каждый эндпоинт сущности — одна функция с типом результата.
4. **Вынеси правила.** Переходы статусов, вычисления, разбор значений — функции в `model/<rule>.ts` с прямым тестом.
   Готово, когда в `api/` и `ui/` не осталось ветвлений предметной логики и у каждого правила есть тест.
5. **Свяжи с соседями.** Тип соседней сущности приходит только через её `@x`-файл (раздел ниже). Готово, когда
   сущность не импортирует ни одной другой сущности через `index.ts`.
6. **Подключи стор, если у сущности есть редьюсер.** Поле добавляется в `StateSchema` через `declare module
   '@/shared/lib/store/StateSchema'` рядом с типом схемы (образец — `entities/User/model/types/user.ts`). Готово,
   когда селекторы и thunk'и берут `StateSchema` и `ThunkConfig` из `shared/lib/store`.
7. **Открой публичный API.** `index.ts` перечисляет экспорты поимённо: функции и константы — `export { … }`, типы —
   `export type { … }`. Готово, когда внешний код получает всё нужное из `@/entities/<Name>`.
8. **Проверь.** `npm run typecheck`, `npm run lint:ts`, `npm test` из `client/` и `npx prettier --write` по новым
   файлам. Готово, когда линтер не выдаёт ни одной ошибки, а тесты правил зелёные.

Новый слайс другого слоя собирается так же: шаги 1, 4, 7 и 8 обязательны для любого слайса.

## Перенос кода между слайсами

1. **Выбери место по таблице «Куда положить код»** из правила. Готово, когда у переносимого кода есть один слайс-владелец.
2. **Перенеси вместе с тестами и стилями**, импорты чужих слайсов — только через их `index.ts`. Готово, когда
   `npm run lint:ts` не выдаёт ошибок слоёв и публичного API.
3. **Сверь страницы, где жил код,** в обеих темах на десктопе и телефоне: TypeScript не видит класс, пропавший из
   SCSS-модуля. Готово, когда страницы выглядят как до переноса.
