# План: подключение Weeztix

Статус: черновик, ждёт входных данных от владельца (раздел «Что нужно от владельца»).
Дата: 2026-10-08.

## Цель

Получать из Weeztix максимум данных — события, цены, заказы, билеты, покупателей — и держать их синхронизированными с CRM.
Weeztix остаётся источником правды по продажам; CRM читает и не изменяет данные в Weeztix, пока не решено иное.

## Что известно об API

Документация прочитана частично: авторизация и список ресурсов описаны, а схемы ответов, пагинация и лимиты запросов
в публичных страницах не видны (схемы подгружаются в браузере). Точный список полей фиксируется на этапе 0 по реальным ответам.

| Тема | Что известно |
|---|---|
| Авторизация | OAuth2 Authorization Code. Вход: `https://login.weeztix.com/login`, токены: `https://auth.weeztix.com/tokens` |
| Срок токенов | В примере access около 3 дней, refresh около года; Weeztix предупреждает, что сроки могут измениться |
| Запросы | `https://api.weeztix.com` (версия 3.0.0), заголовки `Authorization: Bearer …` и `Company: <GUID>` |
| Проверка токена | `GET https://auth.weeztix.com/users/me` |
| Каталог | события, даты, локации, типы билетов с ценами, продукты, магазины, купоны, дополнительные вопросы |
| Заказ | `GET /order/:guid` — билеты, продукты, ответы на вопросы, платежи, возвраты |
| Список заказов | `POST /statistics/search` — не более 1000 заказов за запрос; есть асинхронные экспорты `POST /export` |
| Прочее | сканеры, статистика по заказам и билетам, трекеры магазинов |
| Вебхуки | отдельный сервис `https://webhooks.weeztix.com`; набор событий из документации не виден |

Риски со стороны API:

- Отдельного списка клиентов нет: покупатели и держатели билетов приходят внутри заказов.
- Weeztix пишет, что эндпоинты будут меняться; часть уже помечена устаревшей (`GET /ticket`, `POST /statistics/insights`).
- Пагинация и лимиты запросов не документированы — выясняются на этапе 0.

## Что уже есть в CRM

- Конвейер синхронизации `server/src/modules/ticketing/ticketing.service.ts`: событие → заказ → билеты → люди → регистрации,
  сопоставление по `ExternalIdentity`.
- Модели `Order`, `OrderItem`, `Ticket`, `Payment`, `Refund`, `ProviderConnection` (учётные данные шифруются), `Job`, `SyncRun`.
- Адаптер `server/src/integrations/ticketing/weeztix/WeeztixTicketingProvider.ts` — заглушка, которая намеренно падает,
  чтобы не импортировать фальшивые данные.

Не хватает: входа через OAuth и обновления токена, настоящего адаптера, каталога типов билетов с ценами,
ответов на вопросы, сканов, вебхуков и догоняющей синхронизации.

## Что нужно от владельца

- [ ] Создать OAuth-клиент в Weeztix: Company Settings → OAuth Clients. Redirect URL:
      `http://localhost:18090/api/v1/providers/weeztix/callback`. Разрешён ли localhost, в документации не сказано;
      если нет — нужен https-адрес.
- [ ] Вписать Identifier и Secret в локальный `.env` (не в чат и не в репозиторий). Имена переменных задаются на этапе 0.
- [ ] Один раз войти под пользователем Weeztix с доступом к нужной компании и подтвердить доступ.
- [ ] Назвать компанию, если их в аккаунте несколько.
- [ ] Решить:
  - глубина истории — всё или с какого года;
  - только чтение из Weeztix (рекомендуется) или CRM должна что-то в нём менять;
  - есть ли у CRM публичный https-адрес (без него вебхуки невозможны, остаётся опрос по расписанию);
  - включена ли персонализация билетов (имя держателя на каждом билете) и какие дополнительные вопросы задаются покупателям.

## Этапы

| Этап | Что делаем | Результат |
|---|---|---|
| 0. Подключение и разведка | Вход через OAuth, хранение и обновление токена, проверка связи. По одному образцу каждого ресурса, таблица соответствия полей | Владелец утверждает таблицу: что куда попадает |
| 1. Каталог | События, даты, локации, типы билетов с ценами, магазины | События и цены видны в CRM |
| 2. Продажи | Заказы, билеты, платежи, возвраты, ответы на вопросы; покупатели и держатели → люди и регистрации. История окнами по датам | Полная история продаж, повторный запуск не создаёт дублей |
| 3. Догоняющая синхронизация | Опрос по расписанию, вебхуки при публичном адресе, экран состояния с ошибками и ручным перезапуском | Новые продажи появляются сами |
| 4. Дополнительно | Сканы → check-in, купоны, статистика, панель продаж на странице события | Максимум данных |
| 5. Надёжность | Тесты на сохранённых ответах, проверка прав, поведение при изменении API | Готово к боевому использованию |

Этап 0 не зависит от решений владельца, кроме OAuth-клиента и компании.

## Правила

- Weeztix — источник правды по продажам; поля, изменённые вручную в CRM, синхронизация не затирает.
- Людей объединяем только по внешнему ID или точному email; по похожим именам — никогда (требование спецификации V1, раздел 32).
- Объекты ответа Weeztix не выходят за пределы адаптера; исходный ответ сохраняется рядом с записью.
- Секреты и токены хранятся зашифрованными и не возвращаются через API.
- Миграции только добавляющие; сохранённые ответы для тестов обезличиваются.

## Открытые вопросы

- Формат и лимит пагинации, лимиты запросов.
- Какие события умеют слать вебхуки и как подписывается их содержимое.
- Достаточно ли поиска заказов (1000 за запрос) для истории или нужны экспорты.
- Как сопоставлять события Weeztix с событиями, уже заведёнными в CRM вручную.
