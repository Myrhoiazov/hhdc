## Цель

Получать из Weeztix максимум данных — события, цены, заказы, билеты, покупателей — и держать их синхронизированными с CRM.
Weeztix остаётся источником правды по продажам; CRM читает и не изменяет данные в Weeztix, пока не решено иное.

## Что известно об API

Документация прочитана частично: авторизация и список ресурсов описаны, а схемы ответов, пагинация и лимиты запросов
в публичных страницах не видны (схемы подгружаются в браузере). Точный список полей фиксируется на этапе 0 по реальным ответам.

| Тема | Что известно |
|---|---|
| Авторизация | OAuth2 Authorization Code. Вход: `https://login.weeztix.com/login`, токены: `https://auth.weeztix.com/tokens` |
| Срок токенов | В примере access около 3 дней, refresh около года; Weeztix предупреждает, что сроки могут измениться |
| Запросы | `https://api.weeztix.com` (версия 3.0.0), заголовки `Authorization: Bearer …` и `Company: <GUID>` |
| Проверка токена | `GET https://auth.weeztix.com/users/me` |
| Каталог | события, даты, локации, типы билетов с ценами, продукты, магазины, купоны, дополнительные вопросы |
| Заказ | `GET /order/:guid` — билеты, продукты, ответы на вопросы, платежи, возвраты |
| Список заказов | `POST /statistics/search`, тело `{"search":"","limit":N,"offset":M,"events":[guid]}` — не более 1000 за запрос, без `limit` отдаёт 10; есть асинхронные экспорты `POST /export` |
| Прочее | сканеры, статистика по заказам и билетам, трекеры магазинов |
| Вебхуки | отдельный сервис `https://webhooks.weeztix.com`; набор событий из документации не виден |

Риски со стороны API:

- Отдельного списка клиентов нет: покупатели и держатели билетов приходят внутри заказов.
- Weeztix пишет, что эндпоинты будут меняться; часть уже помечена устаревшей (`GET /ticket`, `POST /statistics/insights`).
- Пагинация поиска заказов — `limit`/`offset` (проверено); каталог отдаётся целиком. Заголовков с лимитами запросов Weeztix не присылает.

## Контакты из Weeztix

`server/src/integrations/ticketing/weeztix/weeztix.contacts.ts` читает заказы и собирает по одному контакту на email;
`server/src/modules/ticketing/weeztix-contacts.service.ts` записывает их как людей.
Эндпоинт `POST /providers/:id/weeztix-contacts` (право `people.import`): без `{"dryRun": false}` — только предпросмотр, в базу не пишет.

| Weeztix (заказ) | CRM | Правило |
|---|---|---|
| `email` | `Person.email` | нижний регистр, без пробелов; ключ сопоставления |
| `firstName`, `lastName` | `Person.firstName`, `lastName`, `displayName` | из последнего заказа; у существующего человека заполняются только пустые |
| ответ `phonenumber` | `Person.phone` | только если пусто |
| ответ `country` | `Person.country` | как ввёл покупатель (встречаются «Germany» и «Deutschland»), только если пусто |
| `locale` (`de_DE`) | `Person.language` (`de`) | только если пусто |
| ответ `keep_me_informed` = 1 | `Consent` MARKETING_EMAIL, GRANTED, источник WEEZTIX, дата заказа | создаётся один раз; согласие или отказ, уже записанные в CRM, не меняются |
| — | `PersonRole` CUSTOMER, `Person.source` = WEEZTIX | источник ставится только новым людям |
| число заказов, дата первого | `ExternalIdentity` (`PERSON`, внешний ID = email) | у Weeztix нет ID покупателя |

Не переносятся на этом шаге: пол, город, возраст (есть в 228 заказах из 1448), UTM-метки и IP покупателя, сами заказы и билеты (этап 2).

Сопоставление: сначала по связи с прошлого импорта, затем по точному email среди активных людей. Если email у двух и более людей —
контакт пропускается и считается отдельно. Повторный запуск дублей не создаёт.

Импорт 2026-10-08: 1168 контактов → 1148 новых людей, 20 привязаны к людям, уже созданным из почты, спорных и ошибок 0;
387 согласий на рассылку. Повторный предпросмотр показывает все 1168 как уже известные.

## Этап 2 — продажи (сделано 2026-10-08)

`server/src/integrations/ticketing/weeztix/weeztix.orders.ts` приводит заказ Weeztix к виду CRM,
`server/src/modules/ticketing/weeztix-orders.service.ts` сохраняет его. Миграций нет.
Эндпоинт `POST /providers/:id/weeztix-sales` (право `ticketing.sync`): обновляет каталог, людей и затем заказы; тот же запуск у `POST /ticketing/sync`.
Экран: кнопка «Обновить заказы и билеты» в панели Weeztix. Старая заглушка (`ticketing.service.ts`, `TicketingProvider.ts`, `WeeztixTicketingProvider.ts`) удалена.

| Weeztix | CRM | Правило |
|---|---|---|
| заказ `guid` | `Order.externalId` | ключ; повторный запуск обновляет |
| `finn_value` / `finn_service_fee` / `finn_price` (центы) | `Order.subtotal` / `fees` / `total` | |
| `status`, `invalidated_reason` | `Order.status` | paid → PAID; returned → REFUNDED; иная отмена → CANCELLED |
| `email` | `Order.buyerPersonId` | человек из импорта контактов; после объединения людей — тот, в кого объединили |
| билеты одного типа | `OrderItem` | цена по прайсу и фактически уплачено (с учётом купона) |
| билет `guid`, `ticket_number` | `Ticket.externalId`, `barcode` | держатель — покупатель: имён держателей в Weeztix нет |
| отмена билета | `Ticket.status` | returned → REFUNDED, swap → TRANSFERRED, иначе CANCELLED; отметка входа, сделанная в CRM, синхронизацией не снимается |
| платёж | `Payment` | сумма списания (с комиссией способа оплаты), способ по названию |
| покупатель + событие | `Registration` (CONFIRMED, источник WEEZTIX) | одна на человека и событие, сколько бы билетов он ни купил; ручная регистрация сохраняется и получает билет |
| весь заказ | `Order.rawData`, `Ticket.rawData` | без IP-адреса, меток отслеживания и геоданных покупателя |

Результат: 1448 заказов (1444 оплачено, 3 отменено, 1 возврат) на 378 392,48 €, 1718 билетов, 1447 платежей, 1394 регистрации.
Полный запуск занимает около 15 секунд; повторный ничего не дублирует.

Известные ограничения:

- 5 заказов содержат билеты на два события: заказ отнесён к событию первого билета, сами билеты — каждый к своему.
- Покупатель нескольких билетов зарегистрирован один; остальные билеты — его гости без имени.
- Возврат отражён статусом заказа и билета; запись `Refund` не создаётся — она описывает возврат, начатый в CRM.
- Ответы на вопросы (пол, город, возраст) лежат в `Order.rawData`, отдельных полей у человека для них нет.
- Запуск идёт внутри HTTP-запроса; на этапе 3 переносится в фоновую задачу.

## Этап 5 — надёжность (сделано 2026-10-08)

- Сохранённые ответы: `server/src/integrations/ticketing/weeztix/fixtures/` — обезличенные ответы каталога, купонов и поиска заказов
  (по одному заказу каждого вида: обычный, с купоном, на два события, отменённый, возвращённый, переданный). Что заменено — в `fixtures/README.md`.
  `weeztix.fixtures.test.ts` проверяет на них, что всё читается, деньги сходятся, билеты ссылаются на типы каталога, а коды — на купоны.
- Изменение API: ответ не в том виде (не список, устаревший эндпоинт со статусом 299, ни один заказ не читается) останавливает синхронизацию
  с ошибкой `WEEZTIX_FORMAT_CHANGED`. Отдельные нечитаемые записи пропускаются, считаются в `unreadable`, а запуск помечается как неуспешный.
  Заказ сохраняется целиком или не сохраняется: нечитаемый билет или платёж делает нечитаемым весь заказ.
- Состояние: итог последней синхронизации пишется в подключение (`lastSyncAt`, `lastError`) и виден на карточке Weeztix в Providers.
  Ошибка данных не отключает Weeztix.
- Права: `weeztix-permissions.test.ts` проверяет, что каждый маршрут Weeztix начинается с проверки нужного права
  (`providers.manage`, `people.import`, `ticketing.sync`, `ticketing.read`, `events.read`, `finance.read`).
- Данные: `GET /orders` и `GET /tickets` больше не отдают исходный ответ Weeztix; ссылки на PDF билетов в CRM не хранятся.

## Этап 3 — опрос по расписанию (сделано 2026-10-08, без вебхуков)

- `server/src/modules/ticketing/weeztix-schedule.ts`: фоновый воркер (тот же, что опрашивает почту) раз в 10 минут читает события, цены, купоны и заказы.
  Настройки: `WEEZTIX_SYNC_ENABLED`, `WEEZTIX_SYNC_INTERVAL_MS` (в `.env.example`). Первый проход — сразу после запуска сервера.
- Заказ, который с прошлого раза не изменился, не переписывается: у сохранённого заказа хранится отпечаток исходного ответа.
  Заказ без покупателя проверяется каждый раз. Счётчики запуска: новые, изменённые, без изменений.
- Одновременно идёт одна синхронизация на подключение: кнопка во время прохода по расписанию отвечает «синхронизация уже идёт».
  Защита работает внутри одного процесса; при отдельном процессе-воркере кнопка и расписание могут совпасть — повторный проход это исправит.
- Подключение со статусом ERROR опрашивается дальше, чтобы восстановиться само.

Не сделано: вебхуки (нет публичного https-адреса).

## Покупки на странице человека (сделано 2026-10-08)

Миграция `20261009180000_order_details` (только добавляющая): у заказа `shopName`, `answers`, `downloadUrl`; у билета `serviceFee`, `downloadUrl`.

- `GET /people/:id/orders` (право `ticketing.read`): заказы, которые человек оформил, и заказы с билетами на его имя, новые сверху.
- Блок «Покупки» на странице человека: заказ раскрывается на месте, как страница заказа в Weeztix — сумма (билеты и сервисный сбор),
  статус, магазин, дата, ответы покупателя, оплата, номер заказа, ссылка на страницу скачивания; по каждому билету — тип, событие,
  штрихкод, отметка входа, цена со сбором, купон и ссылка на файл билета.
- Ссылка на файл билета открывает билет любому, у кого она есть. Поэтому она хранится в отдельном поле, отдаётся только этим
  эндпоинтом и только сотрудникам с правом читать билеты; в копии исходного ответа (`rawData`) ссылок по-прежнему нет.
  Сохраняются только адреса `https://`.
- Название магазина читается из `GET /shop` при каждой синхронизации заказов.

## Финансы и Weeztix (уточнено 2026-10-09)

- Доход в финансах — цена действующих билетов заказа (статусы VALID и USED), то же определение, что на главной. Возвращённые,
  отменённые и переданные билеты дохода не дают. Доход заказа делится между его успешными оплатами пропорционально их размеру;
  неудавшаяся попытка оплаты в делении не участвует.
- Оплата покупателя больше дохода на сервисный сбор магазина и комиссию способа оплаты (`finn_service_fee` платежа):
  по всем оплаченным заказам комиссия способа оплаты — 9 098,96 €. Сумма «оплачено» видна в строке операции.
- Оплата возвращённого или отменённого заказа в доход не входит.
- Финансы считают доход по оплатам, главная — по билетам. Заказ с действующим билетом, но без успешной оплаты, есть только
  на главной: на 2026-10-09 это один заказ от 2026-04-23 с суммой заказа 0 € и билетом на 290 €.

## Сообщения о новых заказах (2026-10-09)

- О заказе сообщается один раз: когда он оплачен, покупатель известен и заказ сделан не раньше суток назад. Заказ помнит,
  что о нём сообщили (`Order.announcedAt`); заказы из истории магазина в чат не попадают.
- В сообщении — типы билетов, событие, имя, почта и страна покупателя, сумма. Это единственное уведомление с данными клиента.

## Правила

- Weeztix — источник правды по продажам; поля, изменённые вручную в CRM, синхронизация не затирает.
- Людей объединяем только по внешнему ID или точному email; по похожим именам — никогда (требование спецификации V1, раздел 32).
- Объекты ответа Weeztix не выходят за пределы адаптера; исходный ответ сохраняется рядом с записью.
- Секреты и токены хранятся зашифрованными и не возвращаются через API.
- Миграции только добавляющие; сохранённые ответы для тестов обезличиваются.

## Открытые вопросы

- Лимиты запросов: заголовков нет, при массовом чтении `GET /order/:guid` нужна осторожная скорость.
- Какие события умеют слать вебхуки и как подписывается их содержимое.
- Как сопоставлять события Weeztix с событиями, заведёнными в CRM вручную: сейчас таких нет, каждое событие Weeztix создаёт своё.
  Если событие завести вручную до синхронизации, появится дубль — нужен выбор «привязать к существующему».
