# План: команда проекта (Event team)

Статус: задачи 1–5 сделаны 2026-10-13. Задача 6 не нужна: владелец выбрал текстовое поле обязанностей.
Дата: 2026-10-13.

Решения владельца от 2026-10-13: задачи участника — текстовое поле; оплата хранится как затраты проекта;
участник команды — `STAFF` или `PARTNER` (партнёрам тоже можно платить); у одного человека может быть несколько
ролей на проекте с разной оплатой, поэтому уникальность — `(eventId, personId, roleTitle)`; гонорары хореографов
остаются на карточке хореографа.

## Цель

На странице проекта (события) появляется блок «Команда»: кто работает на проекте, в какой роли, что делает и сколько
ему платят. Оплата команды попадает в затраты проекта и во все финансовые отчёты без ручного дублирования.

Примеры: администратор проекта — оплата, телефон, email; видеооператор — задачи, оплата.

## Что есть сейчас (инспекция)

| Тема | Состояние |
|---|---|
| Участники | `Registration`, блок «Registrations» на странице события |
| Хореографы | `EventChoreographer` (роль на событии, статусы), блок «Choreographers»; гонорары и расходы — на карточке хореографа (`ChoreographerFeeAgreement`, `ChoreographerCost`) |
| Затраты проекта | `EventExpense`: категория (в т.ч. `SALARY`, `FEE`), сумма, статус `PLANNED/PAID/CANCELLED`, дата, **получатель `personId`** |
| Получатель затраты | Уже выбирается в форме затраты («Paid to»), но только из людей с ролью `CHOREOGRAPHER` или `STAFF` (`server/src/modules/people/payees.ts`) |
| Команда проекта | Нет ничего: ни модели, ни API, ни блока. Роль `STAFF` есть у человека, но к событию он не привязан |
| Задачи | Модель `Task` есть (исполнитель — пользователь системы `User`, поля `eventId`/`personId` без связей), API `/tasks` есть, экрана в клиенте нет |
| Сводка затрат | Читается в четырёх местах: `listEventExpenses`, `eventFinancialOverview`, `ledger.ts`, `dashboard/insights.ts`. Все четыре читают `EventExpense` |

Вывод: вторая половина запроса («при выборе затраты указывать хореографа или участника команды») уже работает.
Не хватает самой команды и связи «участник команды → его оплата».

Попутная находка: в обзоре финансов события (`finance-summary.ts`) категории `SALARY`, `VENUE`, `MARKETING`,
`EQUIPMENT` сливаются в строку `OTHER`. Зарплаты команды там отдельной строкой не видны.

## Ключевое решение: где живёт оплата

**Рекомендация: оплата участника команды — это обычная строка `EventExpense`, привязанная к участнику.**

- У `EventExpense` появляется необязательная ссылка `teamMemberId`.
- При добавлении участника с суммой в той же транзакции создаётся затрата `SALARY` в статусе `PLANNED`.
- Блок «Команда» показывает по участнику «согласовано / выплачено» как сумму его затрат.
- Аванс и остаток — две строки затрат одного участника.

Почему так, а не «сумма в записи участника + производная строка в отчётах» (как сделан гонорар хореографа):

- Четыре отчёта уже читают `EventExpense` — их не нужно менять, двойной счёт невозможен.
- Работают статусы «оплачено / отменено» и дата выплаты. У гонорара хореографа производная строка всегда `PLANNED`.
- Затрата видна на странице человека (блок расходов уже есть).

Цена решения: изменение суммы — это правка затраты, а не поля участника; блок команды даёт для этого кнопку.

## Модель данных

```prisma
model EventTeamMember {
  id        String   @id @default(uuid()) @db.Uuid
  eventId   String   @db.Uuid
  personId  String   @db.Uuid
  roleTitle String             // «Администратор проекта», «Видеооператор» — свободный текст с подсказками
  duties    String?            // задачи и зона ответственности
  notes     String?
  createdAt DateTime @default(now()) @db.Timestamptz(6)
  updatedAt DateTime @updatedAt @db.Timestamptz(6)
  event     Event    @relation(..., onDelete: Cascade)
  person    Person   @relation(..., onDelete: Restrict)
  expenses  EventExpense[]

  @@unique([eventId, personId, roleTitle])
}
// EventExpense: + teamMemberId String? (onDelete: SetNull)
```

- Телефон и email не дублируются: берутся из `Person`, правятся на странице контакта.
- Роль — текст, а не enum: набор ролей у проектов разный, миграция на каждую новую роль не нужна.

## Риски

| Риск | Мера |
|---|---|
| Двойной счёт зарплаты | Оплата хранится только в `EventExpense`; тест на `listEventExpenses`, обзор и ledger |
| Суммы видны тем, кому нельзя | Сервер не отдаёт суммы без `finance.read`; клиент не рисует колонку |
| Удаление и слияние контактов | `person-removal.ts` и слияние учитывают `EventTeamMember` (как `EventChoreographer`) |
| Удаление участника с выплатами | Затраты остаются (ссылка обнуляется, получатель сохраняется); любое удаление требует второго нажатия |
| Миграция | Только новые таблица и колонка, существующие данные не меняются. Применяется при деплое |
