# Код-стайл

Модульный файл правил по конвенции `.claude/rules/` — подхватывается автоматически вместе с
`CLAUDE.md` (импорт не нужен). За архитектурой — в корневой `CLAUDE.md`; этот файл только про
форматирование и стиль.

## Форматирование (задаётся `client/.prettierrc` + ESLint)

- Одинарные кавычки, точка с запятой обязательна, trailing comma — `es5`.
- Отступ 4 пробела (без табов). `printWidth` — 100.
- В `client` есть ESLint (`npm run lint:ts`) и Stylelint (`npm run lint:scss`) — у обоих есть
  вариант `:fix`. Ни один сейчас не является жёстким гейтом в CI: много существующего SCSS не
  проходит `order/properties-order` (порядок свойств) — не нужно массово переформатировать чужие
  файлы ради этого, но и новых нарушений добавлять не стоит.

## TypeScript / React

- Функциональные компоненты, обёрнутые в `memo()` по умолчанию (см. любой компонент в
  `entities/*/ui/*`).
- Слоистая архитектура (Feature-Sliced Design): `app → pages → widgets → features → entities →
  shared`. Слайс импортирует только из публичного API своего слоя (`index.ts`) или слоя ниже —
  никогда не вбок и не вверх. Проверяется `eslint-plugin-denys-fix-fsd-path-plugin`
  (`path-checker`, жёсткая ошибка).
- Алиас пути `@/*` → `client/src/*`. Никогда не импортируй напрямую вглубь чужого слайса —
  импортируй его `index.ts`.
- Включено правило `i18next/no-literal-string` — новый текст в UI должен идти через `t()` (глобально
  через `i18next.configs['flat/recommended']`; для `*.test.*` файлов правило выключено). На
  старых страницах много немигрированных строк; не обязательно чинить их попутно, но и не стоит
  добавлять новые голые строки на русском/английском в компонентах, которые ты активно переписываешь,
  если обернуть их несложно.
- Redux: всегда примонтированные редьюсеры — `user`/`ui`; всё остальное — лениво подключаемый
  слайс через `<DynamicModuleLoader reducers={...}>` на странице/фиче, которая им владеет (полный
  список опциональных слайсов — в `StateSchema.ts`).

## Стилистика — дизайн-система на базе Sero

Это та часть, которая реально важна каждый день: ошибёшься здесь — и страница будет выглядеть как
из другого продукта. Эталон дизайн-системы — набор `-redesigned` токенов, заданный в
`app/styles/themes/{default,dark,orange}.scss`; конкретные паттерны переиспользуй по существующим
формам (см. Правило 3 и упомянутые там файлы).

**Правило 1 — никогда не хардкодь цвет.** Ни сырого hex, ни `rgba()`/`rgb()` для чего-либо
чувствительного к теме (текст, фон, рамки, статусные цвета). Любой цвет — это CSS custom property.

**Правило 2 — используй семейство токенов `-redesigned`, а не старое.** Оба набора существуют
параллельно (`--primary-color` vs `--primary-redesigned`, `--card-bg` vs `--sidebar-bg-redesigned`
и т.д.). Старый набор — до-Sero-эпохи, и некоторые его токены (`--white`, именование
`--dark-bg-redesigned`) ненадёжно переключаются в тёмной теме. Если в файле, который ты правишь,
всё ещё остались старые токены — мигрируй их заодно.

Основные токены (заданы в `default.scss` / `dark.scss`, используются везде):
- Поверхности: `--sidebar-bg-redesigned`, `--sidebar-hover-bg-redesigned`
- Текст: `--sidebar-text-hover-redesigned` (основной), `--sidebar-text-redesigned` (вторичный),
  `--sidebar-group-label-redesigned` (приглушённый/лейблы)
- Рамки: `--card-border-redesigned`
- Акцент бренда: `--primary-redesigned`, `--primary-hover-redesigned`,
  `--primary-soft-bg-redesigned` (мягкий фон для активного/выбранного состояния),
  `--primary-contrast-redesigned` (текст поверх primary)
- Семантика: `--success-bg-redesigned` / `--success-text-redesigned`,
  `--danger-bg-redesigned` / `--danger-text-redesigned`
- Шкала радиусов — всегда токен, никогда сырой px:
  `--radius-sm-redesigned` (8px, инпуты/мелкие кнопки) · `--radius-md-redesigned` (12px, карточки) ·
  `--radius-lg-redesigned` (14px, модалки/крупные карточки) ·
  `--radius-pill-redesigned` (9999px, бейджи/пилюли)
- Категориальная палитра для произвольной цветовой маркировки по элементам (стили танцев, типы
  инцидентов — всё, что нужно раскрасить в N визуально различимых, но не семантических цветов):
  `--style-1-bg/text-redesigned` … `--style-8-*`. Фиксированный порядок оттенков (синий, оранжевый,
  бирюзовый, золотой, розовый, зелёный, фиолетовый, красный), провалидирован на WCAG-контраст и
  различимость для дальтоников в обеих темах — не изобретай 9-й цвет на глаз, переиспользуй слот.
  Назначай детерминированно (хеш от имени), не случайно, чтобы одна и та же сущность всегда получала
  один и тот же цвет. См. `shared/lib/styleColor/styleColor.ts` — эталонный хелпер хеширования.
- Для доменных понятий, которые укладываются в готовую семантику, переиспользуй слот: например,
  3-уровневый бейдж Start/Fan/Pro — это `success` (start) / `style-4` (fan, жёлтый) / `danger`
  (pro) — именно эта тройка уже используется в `GroupCard`, `ChoreographerCard` и
  `ChoreographerModal`; при добавлении четвёртого места с теми же уровнями бери эту тройку, а не
  придумывай новые оттенки.

**Правило 3 — бейджи/пилюли: заливка + тонкая цветная обводка, не только текст, не голая рамка на
`color-mix()`.** Эталон в действующем UI — тройная категория Start/Fan/Pro в
`GroupCard` / `ChoreographerCard` / `ChoreographerModal`:

```scss
/* заливка семантическим фоном + цветная обводка (ChoreographerCard .cat_*) */
background: var(--success-bg-redesigned);
color: var(--success-text-redesigned);
border: 1px solid var(--success-text-redesigned);
```

`GroupCard` `.level_*` — тот же приём от лёгкого варианта (цвет текста + обводка `currentColor`,
`border-radius: 999px`) до полной заливки; оба читаются в обеих темах. Не рисуй пилюлю «текст +
тонкая рамка через `color-mix(in srgb, …, transparent)`» — это раньше было дефолтом на страницах
Mollie и проваливалось в тёмной теме; используй напрямую токены `*-bg-redesigned` /
`*-text-redesigned`.

**Правило 4 — у модалки должен быть собственный непрозрачный фон.** У общего компонента `Modal`
его `.content` по умолчанию откатывается на legacy-токен `--white`, который не переключается в
тёмной теме. У корня/`Card` каждой конкретной модалки должен быть явный
`background: var(--sidebar-bg-redesigned); color: var(--sidebar-text-hover-redesigned);` — если
модалка «залипла светлой» в тёмной теме, проверяй в первую очередь это.

**Правило 5 — тёмная тема реальна, всегда проверяй её.** Переключается классом `app_dark_theme`
(`ThemeProvider`/`useTheme`). `orange.scss` существует, но переключателя для неё нет — не
проектируй под неё. Закончив визуальные правки, реально щёлкни переключатель темы и посмотри, не
полагайся на то, что токены «должны» всё покрывать — токены семейства `--dark-bg-redesigned` и
`--white` уже на этом подводили (см. правила 2/4).

**Использование `color-mix()`:** законно для интенсивности/тонировки (например, сила заливки ячейки
в тепловой карте `MolliePaymentsMatrix`), но не как замена отсутствующего токена. Если тянешься к
`color-mix(in srgb, var(--sidebar-text-hover-redesigned) NN%, transparent)`, чтобы изобразить
приглушённый текст или тонкую рамку — используй напрямую `--sidebar-text-redesigned` /
`--sidebar-group-label-redesigned` / `--card-border-redesigned` — проще и единообразнее с
остальным приложением.

## Конвенции SCSS-модулей

- Один `*.module.scss` на компонент, в той же папке, с тем же базовым именем.
- Корневой класс компонента совпадает с его именем (`.ClientListItem`), BEM-подобные модификаторы —
  отдельные классы (`.SMALL`, `.active`, `.warning`), комбинируются через `classNames()`, а не
  через `&--modifier`.
- Порядок свойств (проверяется Stylelint на новых правках, а не задним числом): позиционирование →
  display/flex → блочная модель (width/height/margin/padding) → текст →
  background/border/radius/shadow → opacity/transition.
