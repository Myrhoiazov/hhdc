# Универсальный архитектурный quality gate

Это обязательный проектный контракт для **всех агентов** и всех создаваемых или существенно
изменяемых исполняемых файлов. Он применяется к production-коду, React-компонентам и хукам,
сервисам, контроллерам, роутерам, middleware, тестам, скриптам, seeds, migrations, build tooling и
конфигурационному коду. Расширение файла и расположение в `client/`, `server/`, `e2e/` или корне
репозитория не создают исключений.

Claude загружает файл по конвенции `.claude/rules/`; остальные агенты обязаны читать его через
глобальное правило в `AGENTS.md`. Этот файл — единственный источник истины по форме функций,
декомпозиции, dead code и опасным паттернам. Правила слоёв и файловой структуры остаются в
`AGENTS.md`, визуальные и SCSS/React-конвенции — в `.claude/rules/code-style.md`, фактическая
конфигурация сканера — в `pyproject.toml`, а новые исключения должны иметь
проверяемое объяснение в задаче или review note.

Проектируй изменение до написания тела функции: границы ответственности, входы, зависимости,
ошибки и проверяемые результаты должны быть ясны заранее. Новый и существенно изменённый код
должен сразу проходить `npm run check:skylos`; quality gate — ограничение проектирования, а не
финальная уборка после реализации.

## Универсальные правила функций и модулей

- Одна функция выполняет один смысловой шаг и имеет имя, описывающее результат или действие.
- Координатор только связывает шаги. Ветвление, преобразование данных, I/O и обработку ошибок
  выноси в именованные функции, если вместе они раздувают координатор.
- Зависимости передавай явно. Когда параметров становится много, группируй их в предметные
  `XxxOptions`, `XxxDeps` или `XxxParams`, а не скрывай в глобальном состоянии.
- Отделяй чистые вычисления от I/O. Чистую логику тестируй напрямую; интеграционный слой оставляй
  тонким.
- Публичный контракт должен скрывать детали реализации. Если сервис используется тремя и более
  модулями, вынеси контракт в отдельный `*.types.ts` или интерфейс.
- Декомпозируй по ответственности, а не ради уменьшения числа строк: вынесенная функция должна
  иметь самостоятельный смысл, ясные входы и проверяемый результат.

## Жёсткие пороги Skylos и проекта

- **Цикломатическая сложность функции ≤ 10** (`SKY-Q301`). Каждый `if`/`else if`/`case`/`&&`/`||`/
  тернарник в теле одной функции — это +1. `switch` на 8+ веток — почти гарантированный провал;
  замени на `Record<Key, Handler>`-таблицу диспетчеризации.
- **Длина функции ≤ 50 строк** (`SKY-C304`). Считается по физическим строкам тела, включая любой
  вложенный код — **в том числе методы объектного литерала, который эта функция возвращает**. Это
  главная ловушка:

  ```ts
  // Skylos видит это как ОДНУ функцию на 60 строк, даже если каждый метод сам по себе короткий:
  export const createXRepository = (): XRepository => ({
      async create(input) { /* 20 строк */ },
      async list(filter) { /* 20 строк */ },
      async getById(id) { /* 20 строк */ },
  });

  // Правильно — методы выносятся в top-level именованные функции, фабрика — только перечисление:
  const createX = async (input: XInput) => { /* 20 строк */ };
  const listX = async (filter: XFilter) => { /* 20 строк */ };
  const getXById = async (id: number) => { /* 20 строк */ };
  export const createXRepository = (): XRepository => ({ create: createX, list: listX, getById: getXById });
  ```

- **≤ 5 параметров на функцию** (`SKY-C303`). С самого начала проектируй 6-й+ параметр как одно
  поле в интерфейсе `XxxOptions`/`XxxDeps`/`XxxParams`, а не добавляй позиционные параметры по
  одному по мере роста функции.
- **Ни одного секрета/высокоэнтропийного литерала в коде** (`SKY-S101`/`SKY-S102`). Только
  `process.env.X` на сервере; в `client/` вообще не должно быть server-only env-имён (Vite/Webpack
  бандлит их в клиентский бинарник) — секреты передаются через API, а не через переменные окружения
  фронтенда.
- **Без опасных паттернов** (`SKY-D2xx`): не собирай `innerHTML` из непроверенной строки без
  `escapeHtml()`-эквивалента; не вызывай `child_process.exec()` с интерполированным вводом — только
  `execFile()` с массивом аргументов; новые GitHub Actions в `.github/workflows/*` — закреплены на
  commit SHA, не на floating-тег.

## Как применять правила в разных частях проекта

- Модуль, сервис, роутер или скрипт: один тонкий координатор + несколько именованных
  функций-шагов уровня "один смысловой шаг = одна функция", а не линейный поток на 100+ строк с
  try/catch на весь метод. Эталон декомпозиции —
  `server/src/modules/ai-email-assistant/simulation.service.ts`
  (`runEmailAssistantSimulation` → `classifyForSimulation`/`retrieveSimulationKnowledge`/
  `generateSimulationDraft`/...) и `draft-pipeline.service.ts` (`runDraftPipeline` →
  `processDraftCandidate`/`recordDraftFailure`).
- Seed, migration, CLI, build- или config-скрипт — **не исключение**: раскладывай
  по тем же смысловым шагам с самого начала (не "потом почищу", см. `test-email-flow.ts`,
  `seed-demo.ts` в чек-листе — оба пришлось разбирать постфактум).
- React-компонент — одна визуальная секция на компонент; как только внутри JSX появляется второй
  логический блок (заголовок+фильтр, таблица+пагинация, секция деталей), выноси его в
  подкомпонент раньше, чем компонент разрастётся за 50 строк (см. `SimulationHistoryPanel.tsx`:
  `ClassificationSection`/`KnowledgeSection`/`DraftSection`/`MetricsSection`,
  `ProviderFilterSelect`/`HistoryTable`/`HistoryTableRow`).
- React-хук — сетевые вызовы и чистую бизнес-логику выносить в обычные функции модуля вне тела
  хука; в самом хуке остаются только `useState`/`useCallback`/`useEffect`-обвязка (см.
  `useSimulationHistory.ts`: `fetchSimulationRunsPage`/`fetchSimulationRunDetail`).
- Большой тестовый файл (>15-20 `test()`) — Skylos считает длину `describe(...)`-колбэка по ВСЕМ
  вложенным тестам вместе, обёртка не спасает от лимита. Варианты: (а) для действительно большого
  файла — делить на несколько файлов по функциональной области с общим `*.testHelpers.tsx` для
  `renderPage`/фикстур; (б) голые top-level `test(...)` без общего `describe()` — Skylos тогда
  меряет длину каждого теста отдельно, а не всей группы (см. прецеденты
  `EmailMessageDetail.test.tsx`, `MollieClientListItem.test.tsx`, и разбор
  `KnowledgeBasePage.*.test.tsx` в волне 6 чек-листа). Для типового файла в пределах лимита ничего
  менять не нужно — это правило про большие файлы, не универсальный запрет на `describe`.

## Dead code и экспорты — не путай реальный мусор с FSD-слепой зоной

`SKY-L012`/`SKY-E003`/`SKY-E004`/`SKY-U001`/`SKY-U003`/`SKY-U004` систематически ложно срабатывают
на: FSD-барреле (`@/`-alias импорт через `index.ts` конкретного слайса — Skylos не резолвит алиасы),
Storybook/Jest-конфиге (`client/config/**`, `*.stories.tsx` — загружаются CLI-конвенцией
инструмента, не прямым импортом), и на точке входа приложения (`client/src/index.tsx` — не входит
ни в чей граф импортов, потому что сам ничем не импортируется). Эти классы уже описаны и занесены в
`ignore`/чек-лист — **не удаляй экспорт только потому, что Skylos назвал его unused**: сначала
`grep` по всему репозиторию (включая barrel `index.ts` слайса) на реальное использование. Реальный
dead code (символ, которого нет нигде, включая баррели) — удаляй, не оставляй "на всякий случай".

## Архитектурная метрика модуля (I/A/D, `SKY-Q802`/`SKY-Q803` — advisory, не блокирует Phase A)

Не входит в `[tool.skylos.gate]`, никогда не провалит `check:skylos`, но задаёт ориентир для нового
модуля: избегай "zone of pain" (модуль конкретный/без абстракции + от него зависит много других
модулей — любое изменение задевает половину графа импортов) и "zone of uselessness" (модуль
полностью абстрактный + у него нет реальных потребителей — мёртвая обёртка на будущее). Практически:
если от нового сервиса будут зависеть 3+ модуля — вынеси его публичный контракт в отдельный
`*.types.ts`/интерфейс, а не завязывай зависящие модули на конкретный класс реализации.

## Перед завершением любого изменения кода

```bash
npm run check:skylos              # полный diff-scan против origin/develop
skylos <изменённый-файл> --quality --danger --secrets   # точечная проверка одного файла
```

- Упало на реальном коде → чини декомпозицией (см. паттерны выше), не глуши находку.
- Уверен, что это false positive из уже описанного класса выше → не трогай код; если класс новый —
  сначала зафиксируй в задаче или review note, что нашлось, почему это false positive и чем
  подтверждено, и только потом — точечно в `ignore`
  `pyproject.toml`, если Skylos действительно уважает `ignore` для этого кода правила (`SKY-A1xx`,
  `SKY-D2xx`, `SKY-L012` — да; `SKY-S101`/`SKY-U00x`/`SKY-E00x` — нет, см. «Известное ограничение
  пайплайна» в чек-листе). Никогда не глуши категорию целиком (`--danger`/`--secrets` из команды
  выше) ради одной находки.
